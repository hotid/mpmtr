# mpmtr — multipath TCP MTR

[Русская версия](README.ru.md) · `man mpmtr` · [documentation](#documentation)

`mpmtr` is a Linux network diagnostic tool for networks with ECMP and other
per-flow load balancing.

`traceroute` and `mtr` do not systematically find the distinct ECMP paths
and do not keep measuring each of them. A destination can answer over one
path while another loses packets or is down: some connections fail, and a
tool that happens to follow a healthy path shows nothing.

mpmtr sends **TCP SYN** probes from many source ports, finds the distinct
routes they take, keeps measuring every route it found, and compares the
failing routes with the healthy ones to narrow down where the fault is.

* **Route discovery** with TTL-limited SYNs, Paris-traceroute style: each
  flow keeps its exact header identity while it is traced.
* **Every discovered route is measured end to end** on `--flows` of its
  source ports (SYN → SYN/ACK or RST), with per-hop ICMP replies like mtr.
* **A live route tree** with per-hop loss and latency.
* **Partial failures**: some routes failing while others are fine; loss and
  RTT degradation per route.
* **Localization**: suspected segments, found by comparing the failing
  routes with the healthy ones.
* **Servers behind one address** told apart by their TCP timestamp clocks
  where those allow it (`--anycast`), each measured through a port that
  reaches it.
* **Plugins**: application checks over a real connection from the measured
  port (`--app`), and names and interfaces of the hops, e.g. over SNMP
  (`--hop-info`).
* **Measurement problems it detects** (capture drops, local send errors,
  ports it cannot measure) are reported as such and not as network loss;
  what cannot be determined is `UNKNOWN` / `INCONCLUSIVE`.
* IPv4 and IPv6, text and JSON reports, JSONL events.

Static binaries, Go, no cgo. No daemon, no service, no mandatory
configuration file: command-line flags and keys only.

## Install

Linux only (IPv4 and IPv6); tested on kernel 7.3.

**Release binaries** (linux/amd64, linux/arm64) are on the
[releases page](https://github.com/hotid/mpmtr/releases). Each archive has
`mpmtr`, the plugins `mpmtr-app-http` (an example) and `mpmtr-hop-snmp`, the
man pages and this README:

```bash
tar xzf mpmtr-*-linux-amd64.tar.gz && cd mpmtr-*-linux-amd64
sudo install -m 0755 mpmtr mpmtr-app-http mpmtr-hop-snmp /usr/local/bin/
sudo install -d /usr/local/share/man/man1 /usr/local/share/man/ru/man1
sudo install -m 0644 man/*.1 /usr/local/share/man/man1/
sudo install -m 0644 man/ru/*.1 /usr/local/share/man/ru/man1/
sudo setcap cap_net_raw,cap_net_admin+ep /usr/local/bin/mpmtr
```

**With Go** (1.26.11 or newer; an older 1.26 downloads that toolchain by
itself). This installs `mpmtr` and the two plugins that come with it into
`/usr/local/bin`, without the man pages:

```bash
CGO_ENABLED=0 GOBIN=/tmp/mpmtr-bin go install github.com/hotid/mpmtr@latest \
    github.com/hotid/mpmtr/cmd/mpmtr-app-http@latest \
    github.com/hotid/mpmtr/cmd/mpmtr-hop-snmp@latest
sudo install -m 0755 /tmp/mpmtr-bin/mpmtr* /usr/local/bin/
sudo setcap cap_net_raw,cap_net_admin+ep /usr/local/bin/mpmtr
```

**From source**:

```bash
git clone https://github.com/hotid/mpmtr && cd mpmtr
make build && sudo make install     # /usr/local/bin, man pages, setcap
```

To run from the source tree without installing: `make setcap` builds
`./mpmtr` and grants it the capabilities (again after every rebuild: a new
file has none).

`make install` honours `PREFIX` and `DESTDIR`. `man mpmtr` is the full
reference; `LANG=ru_RU.UTF-8 man mpmtr` (or `man -L ru mpmtr`) shows the
Russian page. The plugins have pages of their own: `man mpmtr-app-http`,
`man mpmtr-hop-snmp`.

## Quick start

```bash
mpmtr example.com                            # live screen, q quits
mpmtr -r -c 100 example.com                  # report after 100 probes per flow
mpmtr -r -c 100 --json example.com > r.json
mpmtr --discover example.com                 # just find the routes
mpmtr --events ev.jsonl 192.0.2.10:80 example.net   # several targets, events to a file

mpmtr --flows 3 example.com                  # three measured ports per route instead of one
mpmtr --asn --ix example.com                 # name the network of every hop
mpmtr --anycast example.com                  # tell apart the servers behind the address
mpmtr --app http example.com:80              # an HTTP request to every measured server
```

Default port is 443. IPv6 with a port: `'[2001:db8::1]:443'`.
`mpmtr --help` lists all options with examples.

**Capabilities.** Raw sockets and AF_PACKET need `CAP_NET_RAW`. Without it
mpmtr exits with code 4 and prints the `setcap` command. `--fwmark` also needs
`CAP_NET_ADMIN`. Running inside a systemd unit with `RestrictAddressFamilies`
blocks AF_PACKET even when the capability is present.

```
 …
12    │    DST 192.0.2.10                        0.0%   41   173.0   159.6   172.1   158.2   173.0   0.92  ▸ route B OK
```

* **Verdict line** (✔ ✘ ⚠ …) gives the conclusion in one sentence and is never
  stronger than the underlying states.
* **Tree**: hops shared by flows are printed once; the tree branches where
  flows take different observed routes.

  Every branch ends with the DST row of its route, tagged `route X` with its
  state: the *end-to-end TCP result* of the measured ports on that route (the
  DST row's Loss% is the route's loss; Enter opens the route's measured
  flow). Route letters are per session; JSON carries the stable group IDs.
* **Traced vs measured ports**: discovery traces source ports once, in
  order, only to find the routes; `--flows` (default 1) of every route's
  ports are probed end to end continuously (the flow table, `d`, lists
  them). So dozens of ports traced onto one route with one of them measured
  is normal.
* **WARMUP**: a flow needs 30 valid results before it can be called OK or
  LOSS; DOWN is detected earlier, by a run of failures. A route found
  later gets its measured port later, so its flow is in WARMUP for its first
  ~30 s. A warming flow does not make a route, a server or the endpoint UNKNOWN when the
  other flows have a verdict.
* **Flow table** (`d`): `TRACED` says how sure the flow's route is.
  * **`yes`** — traced and repeated; JSON `confirmed`.
  * **`partly`** — incomplete but provably different; `partial_distinct`.
  * **`probably`** — fits one route; `tentative`.
  * **`ambiguous`** — fits several routes and waits; `ambiguous`.
  * **`not yet`** — not traced yet; `unresolved`.

  A legend is printed under the table.
* **Hop columns** follow mtr.
  * **`Loss%`** — the share of unanswered ICMP probes to that hop (shown
    only with ≥3 probes). It is *apparent* loss: routers rate-limit ICMP.
  * **`icmp-limit?`** (flag) — a later hop of the route loses significantly
    less — the 95% intervals do not overlap — which points to the router
    limiting its ICMP answers rather than to loss of forwarded traffic; the
    row is dimmed.
  * **Colours on the live screen** mark what the rows after a hop bear out,
    never a number by itself. A hop's `Loss%` is red when every answering
    hop after it, on every branch under it, loses too, down to a
    destination that loses end to end: that is where the loss starts. A
    router that only answers poorly stays plain. `Last` and `Med` are
    yellow when the round-trip time stands above the row's own earlier
    samples, and on a hop only when the same holds on every hop after it
    and at the destination: the segment where the delay grew. `Last` alone
    is yellow on a DST or server row for one late answer. A row needs
    samples of its own first: 12 answers of a port on a hop (the last 4
    against the 12 before), 24 end-to-end on a DST row. The text report and
    JSON have no colours; JSON has the same marks as
    `loss_persists_downstream`, `rtt_shift` and `rtt_spike`.
  * **`stale`** (flag) — the row's ports have not probed the hop for 30 s
    (at `-i 1`): the hop budget is short (a low `--pps` or `--endpoint-pps`
    with many routes), or one port is in focus (`f`) and the others wait.
  * **`mpls:`** (flag) — RFC 4950 labels: `a/b` is one stack, outermost
    first; `a,b` are different stacks for different ports of the row.
  * **`unstable`** (flag) — several responders.
  * **`* no reply`** — the hop has answered none of the probes sent to it.
  * **`? no reply yet`** — too few probes to tell.
  * **`also answered by later hop X`** — the router of this TTL answers an
    expiring probe and lets the same packet go on, so the routers after it
    answer it too: a probe sent with TTL 3 is then answered by the routers
    of TTL 3, 4 and 5, each quoting it with TTL 1, in varying order.

    A router gets a probe sent with a TTL above its position while the
    packet still has TTL to spare, and forwards it; so it answers only
    probes sent with a TTL up to its position, and the largest TTL it
    answered is its place. This uses the forward path only, not the TTL or
    the order the answers arrive with.

    mpmtr does not make another route, a route change or an unstable hop of
    the early answers, and takes the row's timing from the hop's own router.
  * **`? only later hops answer: X`** — the row when nothing but later
    routers ever answers at a TTL.

  JSON: `also_answered_by` of the hop, `multi_answer` in the measurer
  metrics.
* **Hop annotations** (off by default) name the hop's network at the end of
  FLAGS, where it changes along the route.
  * **`--asn`** — the origin AS (`AS15169 GOOGLE`, Team Cymru bulk whois;
    only public addresses are sent).
  * **`--ix`** — an Internet exchange LAN (`IX:LINX LON1`, PeeringDB
    prefixes cached for a day in `~/.cache/mpmtr`).
  * **`--geoip FILE[,FILE]`** — the country/city (`(DE, Frankfurt)`) and,
    from an ASN database, the AS — offline, from MaxMind GeoLite2 or DB-IP
    lite `.mmdb` files.

  JSON: `ip_info`.
* **Keys**
  * **`d`** — switches tree / flow table / single flow / servers (with
    `--anycast`).
  * **`↑` `↓` `PgUp` `PgDn`** — scroll and select.
  * **`←` `→`**, **`s`** — in the flow table and the server list: sort by
    the previous / next column.
  * **`f`** — in the single-flow view: turns on focus. That port's whole
    route is traced every interval, so its hop rows are fresh, while the hop
    refresh of the other ports waits.
  * **`Enter`** — in the tree: folds or unfolds a hop (and opens the chain
    below it down to the next fork).
  * **`-` `+`** — in the tree: fold or unfold all.
  * **`*`** — in the tree: leaves one line per route (forks stay open).
  * **`Enter`** on a DST or server row — opens its measured flow.
  * **`Esc`** — goes back.
  * **`Tab`** — switches endpoint.
  * **`p`** — pauses the screen (measuring continues).
  * **`r`** — starts a new measurement epoch.
  * **`Ctrl-L`** — redraws the whole screen (after another program wrote
    over it).
  * **`?`** — help.
  * **`q`**, **`Ctrl-C`**, `SIGTERM` — quit; the terminal is restored.

  When stdout is not a terminal, plain-text summaries without ANSI codes are
  printed every 10 s.
* **Bottom lines**
  * **`not yet assigned`** — lists measured ports whose trace still fits
    several routes.
  * **`stopped measuring`** — lists ports stopped because another port
    already measures that route or server.
  * Problem flows are listed with their reason (an INVALID port says why).
  * **`measurer`** — the line shows the tool's own counters:
    * capture drops,
    * skipped slots (never loss),
    * `late` answers (after the deadline),
    * `unexpected` packets (packets on our ports that answer none of our
      probes — another program or prober on the same source port).

## Modes and outputs

All modes use the same measurement core.

| mode | how | output |
|---|---|---|
| live (default) | `mpmtr target` | interactive screen; `-c N` stops after N probes per flow and prints the final report |
| report | `-r [-c N]` (default 100) | text report; `--json` for JSON; exit code |
| discover | `--discover` | route tree and groups after discovery stops |
| events | `--events FILE` / `--events -` | JSONL state transitions; `-` = stdout and no screen |

`-c N` counts probes actually **executed** (sent and resolved), not scheduled
slots. Discovery and hop measurements are bounded by `--report-timeout`
(default 5 min); when it is reached, a partial report with the real counts and
an `INCOMPLETE` mark is printed.

Reports carry a **tcpdump filter** for this run's probes, answers and ICMP
errors (`pcap filter:` line, JSON `parameters.pcap_filter`, and the `?` help
screen): `tcpdump -w mpmtr.pcap '<filter>'` gives a capture for a ticket.

**Exit codes** (report, and live mode with `-c`):

* **0** — all endpoints OK.
* **1** — LOSS/PARTIAL, no DOWN.
* **2** — confirmed DOWN.
* **3** — not enough trustworthy data (UNKNOWN; an OK endpoint where more
  than 25 % of the measured ports have no verdict or cannot be measured; an
  incomplete report — deadline, interrupt, a stopped plugin — unless
  something is confirmed DOWN).
* **4** — parameter or runtime error (the packet capture failing mid-run is
  one: the report is still printed, marked INCOMPLETE).

Priority across endpoints: error > DOWN > UNKNOWN > LOSS > OK.

A short report (`-c` < 30) cannot give OK or LOSS (thirty valid probes are
needed per flow): it ends with 3, or with 2 when the target is down.

`--discover` measures nothing end to end, so its exit code is about the route
list: 0 when discovery ran to its own stop rule, 3 when it was cut short
(`--report-timeout`, interrupt) or found no route, 4 on an error.

`--events -` cannot be combined with `-r` or `--discover`: both write to
standard output. Give `--events` a file there.

**Events**:
`FLOW_DOWN`, `FLOW_RECOVERED`, `FLOW_LOSS`, `FLOW_LOSS_CLEARED`,
`PATHGROUP_DOWN`, `PATHGROUP_LOSS`, `PATHGROUP_RECOVERED`,
`ENDPOINT_DOWN`, `ENDPOINT_LOSS`, `ENDPOINT_RECOVERED`,
`PARTIAL_PATH_FAILURE`, `ROUTE_CHANGED`,
`RTT_DEGRADATION`, `RTT_RECOVERED`,
`MONITORING_IMPAIRED`, `MONITORING_RECOVERED`,
`LOCALIZATION_RESULT`.

* Each event has a stable **`key`** (entity + incident number; a recovery
  carries the key of the incident it ends).
* Simultaneous transitions of several flows are reported once at the highest
  level that describes them (endpoint, then group), with the flows listed.
* **Recovery is never suppressed**: flow recoveries are always emitted, also
  inside an endpoint recovery. A new failure after a recovery is a new
  incident.
* **`LOCALIZATION_RESULT`** is published only when the level or the set of
  suspected segments changes (old/new level, segments with TTLs and
  responders, supporting/contradicting observations, affected groups/flows,
  quality flags). INCONCLUSIVE → INCONCLUSIVE is not an event, leaving a
  confirmed level is.

## Plugins

* **`--app NAME`** — an application check of every measured server: a real
  TCP connection from the measured port itself (so a balancer leads it to
  the same server), handed to the plugin `mpmtr-app-NAME`, which speaks the
  protocol. The checks are counted apart from the TCP probes; three failed
  checks in a row make the server DOWN even while TCP answers.
  `mpmtr-app-http` comes with mpmtr.
* **`--hop-info NAME`** — what a plugin (`mpmtr-hop-NAME`) knows about each
  hop address: a name in place of the bare address and a note in a `PLUGIN`
  column. mpmtr itself sends nothing for this; what may be asked is decided
  by the plugin's own configuration. `mpmtr-hop-snmp` comes with mpmtr and
  asks the router for its name and for the interface that owns the address:

  ```bash
  cat > snmp.conf <<'EOF'
  10.0.0.0/8  community=public
  EOF
  chmod 600 snmp.conf
  mpmtr --hop-info "snmp snmp.conf" example.com:443
  ```

Both are described in [docs/PLUGINS.md](docs/PLUGINS.md); writing one of your
own in [docs/WRITING_PLUGINS.md](docs/WRITING_PLUGINS.md).

## Limitations

* IPv4 and IPv6 only on Linux; raw sockets need `CAP_NET_RAW`.
* External NAT is not detected. A NAT may also re-map the external port when
  its conntrack entry expires; that flow then shows a route change beyond the
  NAT, not loss. Local NAT on the measuring host is detected.
* The kernel's own RST after a SYN/ACK carries the kernel's flow label
  (IPv6) and its own path; mpmtr does not control it.
* Hop `Loss%` describes ICMP replies, not transit traffic. Responder
  addresses do not identify physical links, and ICMP may return on a
  different path than TCP.
* Heavy probing of one 4-tuple interacts with middlebox and server TCP state;
  mpmtr detects the cases it can see (remote state, weak replies) and
  excludes them from loss, but an invisible middlebox policy can still bias
  results.
* One of those exclusions delays DOWN in a rare case. When the RST that ends
  a probe's handshake is lost, the server keeps the half-open connection and
  repeats its SYN/ACK at growing intervals (1 s, 3 s, 7 s … after the first).

  For 3 s after each repeat (three timeouts, if that is longer) an unanswered
  probe of that port is not counted as lost: a server that holds state for
  the 4-tuple may leave a new SYN unanswered.

  If only the forward direction fails right then, the repeats keep arriving,
  and the run of failures that makes the flow DOWN starts later. An outage of
  both directions is not affected: no repeats arrive.
* Bound-only port reservation protects against autobind and other binds, not
  against a privileged process that sends raw packets with the same ports.
