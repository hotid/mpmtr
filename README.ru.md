# mpmtr — многопутевой TCP MTR

[English version](README.md) · `man mpmtr` · [документация](#документация)

`mpmtr` — утилита диагностики сети для Linux, сделанная для сетей с ECMP и
другой балансировкой по соединениям.

`traceroute` и `mtr` не ищут систематически разные пути ECMP и не измеряют
постоянно каждый из них. Адрес может отвечать по одному пути, пока другой
теряет пакеты или не работает вовсе: часть соединений падает, а инструмент,
которому достался здоровый путь, ничего не показывает.

mpmtr шлёт пробы **TCP SYN** с многих исходных портов, находит разные
маршруты, по которым они идут, постоянно измеряет каждый найденный маршрут и
сравнивает плохие маршруты с хорошими, чтобы сузить место отказа.

* **Поиск маршрутов** SYN-пакетами с ограниченным TTL, как Paris traceroute:
  при трассировке поток сохраняет точную идентичность заголовков.
* **Каждый найденный маршрут измеряется насквозь** на `--flows` его
  исходных портах (SYN → SYN/ACK или RST), с ICMP-ответами каждого хопа, как
  в mtr.
* **Живое дерево маршрутов** с потерями и задержкой по хопам.
* **Частичные отказы**: одни маршруты теряют, другие в порядке; потери и
  деградация RTT по маршрутам.
* **Локализация**: подозреваемые участки, найденные сравнением плохих
  маршрутов с хорошими.
* **Серверы за одним адресом** различаются по часам TCP timestamp там, где
  это возможно (`--anycast`), каждый измеряется через порт, который до него
  доходит.
* **Плагины**: проверки приложения по настоящему соединению с измеряемого
  порта (`--app`), имена и интерфейсы хопов, например по SNMP (`--hop-info`).
* **Проблемы измерения, которые он замечает** (потери захвата, локальные
  ошибки отправки, порты, которые нельзя измерить), сообщаются как таковые,
  а не как потери в сети; то, что определить нельзя, — `UNKNOWN` /
  `INCONCLUSIVE`.
* IPv4 и IPv6, текстовые и JSON-отчёты, события JSONL.

Статические бинарники, Go, без cgo. Ни демона, ни сервиса, ни обязательного
файла настроек: только флаги командной строки и клавиши.

> **Код сгенерирован Claude Code** (ИИ-агентом для программирования). К нему
> приложены тесты, но используйте его на свой страх и риск: гарантий нет, см.
> [LICENSE](LICENSE).

## Что он показывает

Один из четырёх путей ECMP теряет всё, остальные три в порядке. Проба,
которой достался здоровый путь, не видит ничего плохого, а одно соединение
из четырёх не устанавливается. `mpmtr -r -c 120` в такой сети (часть колонок
и строк опущена):

По 33 исходным портам найдено четыре маршрута. Каждый измеряется через свой
порт: три отвечают на каждую пробу, четвёртый ни на одну. Дерево маршрутов
показывает, где плохой маршрут расходится с остальными, а локализация
называет участок, который есть только у плохого маршрута, с тем, что
подтверждает вывод и что его ограничивает. Код возврата — 1.

10.11.2.2 не отвечают, поэтому назвать что-то за ним нельзя.

Это стенд из репозитория (`integration/topo.sh`, сетевые пространства имён),
в котором на одном плече отбрасываются все пакеты.

## Установка

Только Linux (IPv4 и IPv6); проверено на ядре 7.3.

**Готовые бинарники** (linux/amd64, linux/arm64) — на
[странице релизов](https://github.com/hotid/mpmtr/releases). В каждом архиве
`mpmtr`, плагины `mpmtr-app-http` (пример) и `mpmtr-hop-snmp`, man-страницы и
README:

```bash
tar xzf mpmtr-*-linux-amd64.tar.gz && cd mpmtr-*-linux-amd64
sudo install -m 0755 mpmtr mpmtr-app-http mpmtr-hop-snmp /usr/local/bin/
sudo install -d /usr/local/share/man/man1 /usr/local/share/man/ru/man1
sudo install -m 0644 man/*.1 /usr/local/share/man/man1/
sudo install -m 0644 man/ru/*.1 /usr/local/share/man/ru/man1/
sudo setcap cap_net_raw,cap_net_admin+ep /usr/local/bin/mpmtr
```

**Через Go** (1.26.11 или новее; более старый 1.26 сам скачает нужный
инструментарий). Так `mpmtr` и два плагина из его состава ставятся в
`/usr/local/bin`, без man-страниц:

```bash
CGO_ENABLED=0 GOBIN=/tmp/mpmtr-bin go install github.com/hotid/mpmtr@latest \
    github.com/hotid/mpmtr/cmd/mpmtr-app-http@latest \
    github.com/hotid/mpmtr/cmd/mpmtr-hop-snmp@latest
sudo install -m 0755 /tmp/mpmtr-bin/mpmtr* /usr/local/bin/
sudo setcap cap_net_raw,cap_net_admin+ep /usr/local/bin/mpmtr
```

**Из исходников**:

```bash
git clone https://github.com/hotid/mpmtr && cd mpmtr
make build && sudo make install     # /usr/local/bin, man-страницы, setcap
```

Чтобы запускать из дерева исходников без установки: `make setcap` собирает
`./mpmtr` и выдаёт ему capability (после каждой сборки заново: у нового
файла их нет).

`make install` учитывает `PREFIX` и `DESTDIR`. `man mpmtr` — полный
справочник; `LANG=ru_RU.UTF-8 man mpmtr` (или `man -L ru mpmtr`) показывает
русскую страницу. У плагинов свои страницы: `man mpmtr-app-http`,
`man mpmtr-hop-snmp`.

## Быстрый старт

```bash
mpmtr example.com                            # интерактивный экран, q — выход
mpmtr -r -c 100 example.com                  # отчёт после 100 проб на поток
mpmtr -r -c 100 --json example.com > r.json
mpmtr --discover example.com                 # только найти маршруты
mpmtr --events ev.jsonl 192.0.2.10:80 example.net   # несколько целей, события в файл

mpmtr --flows 3 example.com                  # три измеряемых порта на маршрут вместо одного
mpmtr --asn --ix example.com                 # назвать сеть каждого хопа
mpmtr --anycast example.com                  # различить серверы за адресом
mpmtr --app http example.com:80              # HTTP-запрос к каждому измеряемому серверу
```

Порт по умолчанию 443. IPv6 с портом: `'[2001:db8::1]:443'`.
`mpmtr --help` перечисляет все опции с примерами.

**Права.** Сырым сокетам и AF_PACKET нужна `CAP_NET_RAW`. Без неё mpmtr
завершается с кодом 4 и печатает команду `setcap`. `--fwmark` нужна ещё
`CAP_NET_ADMIN`. Юнит systemd с `RestrictAddressFamilies` блокирует
AF_PACKET даже при наличии capability.


Сам экран на английском; ниже — что означают его части.

* **Строка вердикта** (✔ ✘ ⚠ …) даёт вывод одним предложением и никогда не
  сильнее состояний под ней.
* **Дерево**: хопы, общие для потоков, печатаются один раз; дерево ветвится
  там, где потоки идут разными наблюдаемыми маршрутами.

  Каждая ветка заканчивается строкой DST своего маршрута с меткой `route X`
  и состоянием: это *сквозной результат TCP* измеряемых портов маршрута
  (Loss% строки DST — потери маршрута; Enter открывает измеряемый поток
  маршрута). Буквы маршрутов действуют в пределах сеанса; в JSON —
  постоянные идентификаторы групп.
* **Трассированные и измеряемые порты**: поиск маршрутов один раз
  трассирует исходные порты по порядку, только чтобы найти маршруты;
  `--flows` (по умолчанию 1) портов каждого маршрута постоянно измеряются
  насквозь (их перечисляет таблица потоков, `d`). Поэтому десятки
  трассированных портов на одном маршруте при одном измеряемом — норма.
* **WARMUP**: потоку нужно 30 годных результатов, чтобы назвать его OK или
  LOSS; DOWN обнаруживается раньше, по серии отказов. Маршрут, найденный
  позже, позже получает свой измеряемый порт, и его поток первые ~30 с в
  WARMUP. Прогревающийся поток не делает маршрут, сервер или адрес UNKNOWN, если у
  остальных потоков вердикт есть.
* **Таблица потоков** (`d`): `TRACED` говорит, насколько известен маршрут
  потока.
  * **`yes`** — трассирован и подтверждён; в JSON `confirmed`.
  * **`partly`** — неполный, но доказуемо отличается; `partial_distinct`.
  * **`probably`** — подходит к одному маршруту; `tentative`.
  * **`ambiguous`** — подходит к нескольким маршрутам и ждёт; `ambiguous`.
  * **`not yet`** — ещё не трассирован; `unresolved`.

  Под таблицей печатается легенда.
* **Колонки хопов** как в mtr.
  * **`Loss%`** — доля проб к хопу без ответа ICMP (показывается от 3 проб).
    Это *кажущиеся* потери: маршрутизаторы ограничивают частоту ICMP.
  * **`icmp-limit?`** (флаг) — у одного из следующих хопов маршрута потерь
    значимо меньше — 95-процентные интервалы не пересекаются, — что указывает
    на ограничение частоты ответов ICMP на маршрутизаторе, а не на потери
    транзитного трафика; строка приглушена.
  * **Цвета на живом экране** отмечают то, что подтверждают строки после
    хопа, а не число само по себе. `Loss%` хопа красный, когда теряет и
    каждый отвечающий хоп после него, на каждой ветке под ним, вплоть до
    адресата, теряющего пробы из конца в конец: здесь потери начинаются.
    Маршрутизатор, который просто плохо отвечает, не красится. `Last` и
    `Med` жёлтые, когда задержка выше прежних замеров этой же строки, а на
    хопе — только если то же видно на каждом хопе после него и у адресата:
    это участок, где задержка выросла. Один только `Last` жёлтый на строке
    DST или сервера при одном позднем ответе. Строке сначала нужны свои
    замеры: 12 ответов порта на хопе (последние 4 против 12 до них), 24
    сквозных на строке DST. Текстовый отчёт и JSON без цветов; в JSON те
    же отметки — `loss_persists_downstream`, `rtt_shift` и `rtt_spike`.
  * **`stale`** (флаг) — порты строки не пробовали хоп 30 с (при `-i 1`):
    не хватает бюджета проб хопов (низкий `--pps` или `--endpoint-pps` при
    множестве маршрутов) или один порт в фокусе (`f`), и остальные ждут.
  * **`mpls:`** (флаг) — метки RFC 4950: `a/b` — один стек, внешняя первой;
    `a,b` — разные стеки для разных портов строки.
  * **`unstable`** (флаг) — несколько отвечающих.
  * **`* no reply`** — хоп не ответил ни на одну из посланных ему проб.
  * **`? no reply yet`** — проб пока мало, чтобы судить.
  * **`also answered by later hop X`** — роутер этого TTL отвечает на
    истекающую пробу и при этом пропускает тот же пакет дальше, поэтому на
    неё отвечают и следующие роутеры: на пробу с TTL 3 тогда отвечают
    роутеры с TTL 3, 4 и 5, каждый цитирует её с TTL 1, порядок ответов
    меняется.

    Пробу, посланную с TTL больше своей позиции, роутер получает с запасом
    TTL и пересылает; значит, он отвечает только на пробы с TTL не больше
    своей позиции, и наибольший TTL, на который он ответил, — его место.
    Правило опирается только на прямой путь, а не на TTL или порядок
    пришедших ответов.

    Из ранних ответов mpmtr не делает другой маршрут, смену маршрута или
    нестабильный хоп и берёт время строки только по ответам самого хопа.
  * **`? only later hops answer: X`** — так выглядит строка, если на TTL
    отвечают только дальние роутеры.

  В JSON: `also_answered_by` у хопа, `multi_answer` в метриках измерителя.
* **Сведения о сетях хопов** (по умолчанию выключены) называют сеть хопа в
  конце FLAGS там, где она меняется вдоль маршрута.
  * **`--asn`** — AS, анонсирующая адрес (`AS15169 GOOGLE`, массовый whois Team Cymru;
    отправляются только публичные адреса).
  * **`--ix`** — пиринговая сеть точки обмена трафиком и участник IX, чей
    маршрутизатор стоит на этом адресе (`IX:LINX LON1 member AS15169 Google
    LLC`; префиксы и адреса участников из PeeringDB, кэш на сутки в
    `~/.cache/mpmtr`). PeeringDB ограничивает клиентов, которые часто
    спрашивают без учётной записи (HTTP 429 до часа); отказанный список
    запрашивается снова через час, и об этом предупреждает сообщение (см.
    «Ограничения»).
  * **`--geoip ФАЙЛ[,ФАЙЛ]`** — страна/город (`(DE, Frankfurt)`), а из базы
    ASN — и AS, офлайн, по файлам `.mmdb` MaxMind GeoLite2 или DB-IP lite.

  В JSON — `ip_info`.
* **Клавиши**
  * **`d`** — переключает дерево / таблицу потоков / один поток / серверы
    (с `--anycast`).
  * **`↑` `↓` `PgUp` `PgDn`** — прокручивают и выбирают.
  * **`←` `→`**, **`s`** — в таблице потоков и списке серверов: сортируют
    по предыдущей / следующей колонке.
  * **`f`** — в виде одного потока: включает фокус. Весь маршрут этого порта
    трассируется каждый интервал, и строки его хопов свежие, а обновление
    хопов остальных портов на это время ждёт.
  * **`Enter`** — в дереве: сворачивает или разворачивает хоп (и раскрывает
    цепочку под ним до следующей развилки).
  * **`-` `+`** — в дереве: сворачивают или разворачивают всё.
  * **`*`** — в дереве: оставляет по одной строке на маршрут (развилки
    остаются раскрытыми).
  * **`Enter`** на строке DST или сервера — открывает его измеряемый поток.
  * **`Esc`** — назад.
  * **`Tab`** — переключает адрес.
  * **`p`** — ставит экран на паузу (измерения идут).
  * **`r`** — начинает новую эпоху измерений.
  * **`Ctrl-L`** — перерисовывает весь экран (если поверх него написала
    другая программа).
  * **`?`** — справка.
  * **`q`**, **`Ctrl-C`**, `SIGTERM` — выход; терминал восстанавливается.

  Если stdout не терминал, каждые 10 с печатаются текстовые сводки без
  ANSI-кодов.
* **Нижние строки**
  * **`not yet assigned`** — измеряемые порты, чья трасса пока подходит к
    нескольким маршрутам.
  * **`stopped measuring`** — порты, остановленные потому, что этот маршрут
    или сервер уже измеряет другой порт.
  * Проблемные потоки перечислены с причиной (порт INVALID говорит, почему).
  * **`measurer`** — строка с собственными счётчиками утилиты:
    * потери захвата,
    * пропущенные слоты (никогда не потери),
    * `late` (ответы после срока),
    * `unexpected` (пакеты на наши порты, не отвечающие ни на одну нашу
      пробу, — этот же исходный порт использует другая программа или зонд).

## Режимы и вывод

Все режимы используют одно и то же ядро измерений.

| режим | как | вывод |
|---|---|---|
| интерактивный (по умолчанию) | `mpmtr цель` | экран; `-c N` останавливается после N проб на поток и печатает итоговый отчёт |
| отчёт | `-r [-c N]` (по умолчанию 100) | текстовый отчёт; `--json` для JSON; код возврата |
| поиск | `--discover` | дерево маршрутов и группы после остановки поиска |
| события | `--events ФАЙЛ` / `--events -` | переходы состояний в JSONL; `-` = stdout и без экрана |

`-c N` считает реально **выполненные** пробы (отправленные и завершённые), а
не запланированные слоты. Поиск маршрутов и измерения хопов ограничены
`--report-timeout` (по умолчанию 5 мин); по его истечении печатается
частичный отчёт с реальными счётчиками и пометкой `INCOMPLETE`.

Отчёты содержат **фильтр для tcpdump** — пробы, ответы и ICMP-ошибки этого
запуска (строка `pcap filter:`, в JSON `parameters.pcap_filter`, и на экране
справки `?`): `tcpdump -w mpmtr.pcap '<фильтр>'` даёт запись для тикета.

**Коды возврата** (отчёт и живой режим с `-c`):

* **0** — все адреса OK.
* **1** — LOSS/PARTIAL, без DOWN.
* **2** — подтверждённый DOWN.
* **3** — недостаточно достоверных данных (UNKNOWN; адрес OK, у которого
  больше 25 % измеряемых портов без вердикта или не поддаются измерению;
  неполный отчёт — истёк срок, прерван, остановился плагин — если при этом
  нет подтверждённого DOWN).
* **4** — ошибка параметров или выполнения (в том числе отказ захвата
  пакетов посреди запуска: отчёт всё равно печатается с пометкой
  INCOMPLETE).

Приоритет по адресам: ошибка > DOWN > UNKNOWN > LOSS > OK.

Короткий отчёт (`-c` < 30) не может дать OK или LOSS (на поток нужно
тридцать действительных проб): он заканчивается кодом 3, а если адресат
лежит — кодом 2.

`--discover` ничего не измеряет насквозь, поэтому его код говорит о списке
маршрутов: 0 — поиск дошёл до своего правила остановки, 3 — оборван
(`--report-timeout`, прерывание) или не нашёл ни одного маршрута, 4 — ошибка.

`--events -` нельзя сочетать с `-r` и `--discover`: оба пишут в стандартный
вывод. Там укажите для `--events` файл.

**События**:
`FLOW_DOWN`, `FLOW_RECOVERED`, `FLOW_LOSS`, `FLOW_LOSS_CLEARED`,
`PATHGROUP_DOWN`, `PATHGROUP_LOSS`, `PATHGROUP_RECOVERED`,
`ENDPOINT_DOWN`, `ENDPOINT_LOSS`, `ENDPOINT_RECOVERED`,
`PARTIAL_PATH_FAILURE`, `ROUTE_CHANGED`,
`RTT_DEGRADATION`, `RTT_RECOVERED`,
`MONITORING_IMPAIRED`, `MONITORING_RECOVERED`,
`LOCALIZATION_RESULT`.

* У каждого события стабильный **`key`** (сущность + номер инцидента;
  восстановление несёт ключ инцидента, который завершает).
* Одновременные переходы нескольких потоков сообщаются один раз на самом
  высоком уровне, который их описывает (адрес, затем группа), со списком
  потоков.
* **Восстановление никогда не подавляется**: восстановления потоков выдаются
  всегда, в том числе внутри восстановления адреса. Новая неудача после
  восстановления — новый инцидент.
* **`LOCALIZATION_RESULT`** публикуется только при смене уровня или набора
  подозрительных участков (старый/новый уровень, участки с TTL и
  отвечающими, подтверждающие и противоречащие наблюдения, затронутые
  группы/потоки, флаги качества). INCONCLUSIVE → INCONCLUSIVE — не событие,
  уход с подтверждённого уровня — событие.

## Плагины

* **`--app ИМЯ`** — проверка приложения на каждом измеряемом сервере:
  настоящее TCP-соединение с самого измеряемого порта (поэтому балансировщик
  ведёт его на тот же сервер) передаётся плагину `mpmtr-app-ИМЯ`, который
  говорит по протоколу. Проверки считаются отдельно от TCP-проб; три
  неудачные проверки подряд делают сервер DOWN, даже пока TCP отвечает.
  `mpmtr-app-http` входит в состав mpmtr.
* **`--hop-info ИМЯ`** — что плагин (`mpmtr-hop-ИМЯ`) знает о каждом адресе
  хопа: имя вместо голого адреса и примечание в колонке `PLUGIN`. Сам mpmtr
  для этого ничего не отправляет; что можно спрашивать, решает собственная
  настройка плагина. `mpmtr-hop-snmp` входит в состав mpmtr и спрашивает у
  маршрутизатора его имя и интерфейс, которому принадлежит адрес:

  ```bash
  cat > snmp.conf <<'EOF'
  10.0.0.0/8  community=public
  EOF
  chmod 600 snmp.conf
  mpmtr --hop-info "snmp snmp.conf" example.com:443
  ```

Оба вида описаны в [docs/PLUGINS.ru.md](docs/PLUGINS.ru.md); как написать
свой — в [docs/WRITING_PLUGINS.ru.md](docs/WRITING_PLUGINS.ru.md).

## Ограничения

* Только IPv4 и IPv6 на Linux; сырым сокетам нужна `CAP_NET_RAW`.
* Внешний NAT не обнаруживается. NAT может переназначить внешний порт, когда
  истекает его запись conntrack; тогда поток показывает смену маршрута за
  NAT, а не потери. Локальный NAT на измеряющем хосте обнаруживается.
* Собственный RST ядра после SYN/ACK несёт flow label ядра (IPv6) и идёт
  своим путём; mpmtr им не управляет.
* `Loss%` хопа описывает ICMP-ответы, а не транзитный трафик. Адреса
  отвечающих не идентифицируют физические каналы, а ICMP может возвращаться
  другим путём, чем TCP.
* Интенсивные пробы одного 4-tuple взаимодействуют с состоянием TCP
  промежуточных устройств и сервера; mpmtr обнаруживает видимые ему случаи
  (состояние на сервере, слабые ответы) и исключает их из потерь, но невидимая
  политика промежуточного устройства всё равно может исказить результат.
* Одно из этих исключений в редком случае задерживает DOWN. Когда теряется
  RST, закрывающий рукопожатие пробы, сервер держит полуоткрытое соединение
  и повторяет свой SYN/ACK с растущими интервалами (через 1 с, 3 с, 7 с …
  после первого).

  В течение 3 с после каждого повтора (трёх таймаутов, если это дольше)
  безответная проба этого порта не считается потерянной: сервер, который
  держит состояние для 4-tuple, может не ответить на новый SYN.

  Если именно в этот момент отказывает только прямое направление, повторы
  продолжают приходить, и серия отказов, которая делает поток DOWN,
  начинается позже. Отказ обоих направлений это не затрагивает: повторы не
  приходят.
* Резервирование портов через bind защищает от autobind и других bind, но не
  от привилегированного процесса, шлющего сырые пакеты с теми же портами.
* `--ix` зависит от PeeringDB, а он ограничивает анонимных клиентов:
  несколько первых загрузок за короткое время (несколько хостов за одним
  адресом, очищенный кэш) могут получить отказ до часа. До тех пор IX-хопы
  не отмечаются (или отмечаются по старому кэшу, или без участника);
  предупреждение говорит, когда будет следующая попытка.
