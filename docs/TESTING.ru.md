# Тесты и производительность

[English version](TESTING.md) · [README](../README.ru.md)

Что покрывают тесты, как их запускать, и результаты замеров производительности.

## Тесты

```bash
make test           # юнит-тесты + детерминированные сценарии (симулированная сеть, виртуальные часы)
make race           # то же с -race
make vet            # go vet и gofmt
make integration    # root: сетевые пространства имён, veth, ECMP, tc netem (≈20 мин)
make bench          # синтетические бенчмарки ядра
make man-check      # man-страницы рендерятся без предупреждений
```

Измерительное ядро mpmtr само ввода-вывода не делает: пробы уходят через
`Transport`, пакеты и отметки полноты захвата приходят через методы, время —
через `Clock`. Симулированная
сеть в `internal/core/sim_test.go` (пути по потокам, потери ICMP по хопам,
транзитные потери, RTT, unreachable, пропавший RST, потери захвата) за
миллисекунды прогоняет сценарии и инварианты:

* один мёртвый поток из 16,
* ноль годных проб,
* быстрый DOWN,
* 12 DOWN + 4 UNKNOWN,
* эпохи восстановления,
* абсолютная и относительная деградация RTT,
* ветки со скрытыми хопами,
* нетранзитивность неизвестных хопов,
* потери захвата,
* поздний SYN/ACK,
* дедупликация событий (одно главное событие на группу, восстановление
  никогда не подавляется),
* откладывание хопов при насыщенном расписании сквозных проб,
* все причины остановки поиска,
* локализация с контролем и без,
* смены маршрутов,
* ограничение частоты ICMP,
* сопоставление слабых, повторных и поздних ответов и запасное сопоставление цитат,
* локальный NAT,
* неотправленные SYN,
* нехватка бюджета планировщика,
* нехватка бюджета на опрос хопов,
* достижимость выхода из LOSS,
* сброс статистики,
* монотонные ISN,
* маршруты разной длины при параллельном опросе TTL,
* хопы, взятые у других портов, помечены как допущение,
* обрыв на потоке с фоновыми потерями становится DOWN по порогу, который
  фон задал до его начала,
* перепись серверов: равные и «лёгкие» серверы, неразличимые часы, сервер,
  умерший после переписи, сервер, вышедший из пула, выдуманный сервер,
  настоящий сервер с одним чужим портом,
* проверки приложения: счёт отдельно от TCP, мёртвое и нестабильное
  приложение, TCP и приложение восстанавливаются каждый сам по себе,
* плагин приложения, который не отвечает, останавливается.

Интеграционные тесты (`integration/`, тег сборки `integration`) используют
топологию из `integration/topo.sh`: `src ═ R0 ═ ECMP R1..R4 ═ RD ─ dst`,
multipath с L4-хэшем в обе стороны, IPv4+IPv6. Перед проверкой поиска
маршрутов tcpdump на четырёх плечах подтверждает, что исходные порты
действительно расходятся по плечам. Тесты покрывают:

* потери на одном плече,
* потери на общем участке,
* рост RTT на одном плече и общий (база),
* падение адресата,
* маршрутизаторы без ICMP,
* ограничение частоты ICMP,
* смену маршрута на ходу,
* локальный SNAT,
* конфликт портов,
* потери захвата (крошечное кольцо под нагрузкой),
* неверный ACK от промежуточного устройства,
* поздний SYN/ACK,
* SYN по IPv6 через raw-сокет с flow label/traffic class на проводе,
* резервирование портов без прослушивания и RST ядра (IPv4/IPv6),
* метки времени ядра TX/RX против задержки netem,
* режим поиска,
* локальный ECMP,
* промежуточное устройство с conntrack на пути,
* одно плечо на три маршрутизатора длиннее остальных,
* приложение отвечает бессмыслицей, пока TCP отвечает,
* плагины сведений о хопах.

Тестами не покрыто: сервер, добавленный в пул балансировщика после переписи
(его не ищут, см. [ANYCAST.ru.md](ANYCAST.ru.md)), сервер, у которого
смещение часов меняется, а машина остаётся той же, и путь, который
пропускает SYN, но теряет данные проверки приложения (проверка тогда не
проходит, как любая другая; различить эти случаи нечем).

Им нужны root и сетевые пространства имён, поэтому CI гоняет только юнит- и
сценарные тесты; без root `make integration` завершается ошибкой, а не
пропуском.

## Производительность

Синтетические бенчмарки ядра (`make bench`, без системных вызовов, включают
стоимость самого симулятора; i7, 8 потоков, Go 1.26):

| потоков | проб/с (сим.) | CPU ядра на секунду | аллокаций/пробу | heap |
|---:|---:|---:|---:|---:|
| 320 | 320 | 1,7 мс | 14,5 | 2,4 МБ |
| 3 200 | 3 200 | 17,6 мс | 14,5 | 15 МБ |
| 32 000 | 32 000 | 143 мс | 14,0 | 198 МБ |
| 32 000, шторм таймаутов | 31 900 | 84 мс | 8,0 | 154 МБ |
| 3 200 + поиск маршрутов | 5 760 | 35 мс | 11,9 | 80 МБ |

Перегруппировка 256 наблюдаемых потоков на 64 маршрутах занимает 0,35 мс.
Симулятор шагает по 10 мс, поэтому его задержка планировщика равна шагу и не
приводится.

Настоящие сокеты, стенд из netns на том же 8-поточном ноутбуке
(`integration/bench_throughput.sh EPS FLOWS COUNT`, только сквозные пробы, 1
проба/с на поток; маршрутизаторы, ядро адресата, отвечающее на каждый SYN, и
наше ядро, шлющее каждый RST, делят один CPU):

| потоков | сквозных проб | сопоставлено SYN/ACK | таймаутов | потерь захвата | пропущенных слотов | задержка планировщика ср. / макс. | CPU (user+sys) | макс. RSS |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 3 200 (25×128) | 128 000 за 40 с | 128 000 | 0 | 0 | 47 (0,04 %) | 0,47 / 41 мс | 8,0 с / 40 с (20 % ядра) | 108 МБ |
| 32 000 (125×256) | 640 000 за 21 с (≈30 000/с) | 640 000 | 0 | 0 | 3 646 (0,6 %, общий бюджет PPS при старте) | 0,80 / 135 мс | 16,9 с / 21,8 с (78 % ядра, ⅔ в системных вызовах) | 612 МБ |

32 000 потоков в этой конфигурации измеряются без потерь измерений.
Узкое место — `sendmsg` на каждый пакет и обработка кольца в ядре (системное
время), затем память: ~6 КБ состояния ядра на поток плюс итоговый JSON-снимок
всех потоков в режиме отчёта.

Поиск маршрутов и пробы хопов добавляют состояние хопов на (поток, TTL); при
32 000 потоков их ограничивает бюджет на отвечающего, а не CPU. Эти цифры
получены на одной машине и виртуальном стенде; для другого железа это не
гарантия.
