# Плагины

[English version](PLUGINS.md)

Как написать свой плагин — в [WRITING_PLUGINS.ru.md](WRITING_PLUGINS.ru.md).
У плагинов из поставки есть man-страницы: `man mpmtr-app-http`,
`man mpmtr-hop-snmp`.

Плагины двух видов, и те и другие — отдельные исполняемые файлы, которые
запускает mpmtr: [проверки приложения](#плагины-проверки-приложения)
(`--app`) и [сведения о хопах](#плагины-сведений-о-хопах) (`--hop-info`).

## Плагины проверки приложения

mpmtr измеряет пути и серверы только средствами TCP. Плагин добавляет
проверку каждого измеряемого сервера на уровне приложения: `mpmtr --app ИМЯ`
запускает исполняемый файл `mpmtr-app-ИМЯ` (рядом с mpmtr или в `PATH`;
можно и `--app ПУТЬ`); `--app "ИМЯ АРГУМЕНТЫ..."` передаёт плагину его
собственные аргументы (аргумент с пробелами берётся внутри в одинарные
кавычки). Раз в `--app-interval` (по умолчанию 10 с) для каждого
измеряемого порта mpmtr

1. открывает настоящее TCP-соединение ядра **с этого порта** — тот же
   4-tuple, что и у его TCP-проб, с теми же TOS и меткой потока IPv6, поэтому
   балансировщик ведёт его на тот же сервер (с `--anycast` — ровно на тот сервер, который этот порт измеряет);
2. передаёт подключённый сокет плагину, который говорит по своему протоколу;
3. закрывает соединение RST (без TIME_WAIT; сервер и промежуточные
   устройства с состоянием сбрасывают его до следующей пробы).

Пока идёт проверка, сырые пробы порта приостанавливаются (эти слоты считаются
пропущенными, никогда не потерями), а пакеты соединения не принимаются за
ответы на пробы. Исходы — в статистике порта (и его сервера):

| исход | для TCP | для приложения |
|---|---|---|
| протокол пройден | ответ (RTT = рукопожатие соединения) | пройденная проверка |
| протокол не пройден (соединились или получили отказ) | ответ | непройденная проверка |
| нет ответа на SYN | таймаут | — |
| проблема плагина (упал, не ответил, локальная ошибка) | локальная ошибка: ни то, ни другое | — |

Проверки считаются отдельно от TCP-проб: `app_checks`, `app_failed` и
`app_failure_rate` в JSON, флаг `app-failed:N/M` у потока, «application
checks: N of M failed» в вердикте. Их гораздо меньше, чем проб (одна на
`--app-interval`), поэтому с пробами они никогда не складываются, и у них
своё состояние:

* три непройденные проверки подряд делают порт **DOWN** (причина
  `app_down`), хотя TCP отвечает; две пройденные подряд возвращают его;
* проверки, которые не проходят время от времени, делают его **LOSS** — по
  тому же критерию, что и для проб, но только по проверкам.

`-c` считает только TCP-пробы; проверки идут сверх них, вне лимитов `--pps`.
Проверки ждут окончания поиска маршрутов и переписи, и каждая начинается
сразу после отвеченной сквозной пробы своего порта: проба с ограниченным TTL
оставляет 4-tuple полуоткрытым на NAT с состоянием (SYN_SENT с нашим seq), и
настоящее соединение, открытое в этот момент, зависает, если ISN ядра
окажется меньше.

Плагин работает с правами mpmtr (под sudo — root), поэтому это должна быть
программа, которой вы доверяете; если он умер, отчёт помечается INCOMPLETE с
указанием причины.

### Протокол

fd 3 плагина — unix-сокет `SOCK_SEQPACKET`; каждое сообщение — один объект
JSON в одном пакете.

```
плагин → mpmtr  {"type":"hello","name":"http","version":"1"}
mpmtr → плагин  {"type":"check","id":7,"src":"192.0.2.1","sport":20031,
                 "dst":"192.0.2.10","dport":443,"server":"S7",
                 "host":"example.com","timeout_ms":5000}
                 + подключённый TCP-сокет (SCM_RIGHTS)
плагин → mpmtr  {"type":"result","id":7,"ok":false,"stage":"handshake",
                 "error":"eof","ms":12.5}
плагин → mpmtr  {"type":"result","id":8,"ok":true,"note":"200","ms":9.1}
```

* `hello` — первым, в течение 5 с.
* Проверки могут приходить одновременно; отвечайте на каждую с её `id`.
* Закройте свою копию сокета до ответа; последнюю закрывает mpmtr.
* Отвечайте в пределах `timeout_ms`; mpmtr сдаётся секундой позже
  (локальная ошибка). Плагин, оставивший без ответа три проверки подряд,
  останавливается, чтобы закрылись соединения, которые он ещё держит; отчёт
  тогда INCOMPLETE.
* `stage` называет своими словами этап, на котором проверка не прошла;
  `stage:"plugin"` отмечает проблему на стороне плагина (локальная ошибка, не
  вина сервера).
* `note` необязателен: несколько символов об ответе (статус HTTP, версия),
  не больше 24. Показывается в колонке `PLUGIN` той строки, где стоят
  сквозные числа порта (строка DST маршрута или строка сервера с
  `--anycast`), в JSON это `app_note` потока. Берётся от последней проверки,
  на которую сервер ответил; если порты одной строки получили разное,
  показывается каждое по разу (`200|503`). `mpmtr-app-http` присылает код
  статуса.
* `server` — имя сервера за адресом в mpmtr (`--anycast`).
* `host` — цель, как она набрана в командной строке mpmtr, без порта: имя
  или адрес. Плагин, которому нужно имя (заголовок `Host` в HTTP, имя
  сервера в TLS), берёт его отсюда.
* stderr сохраняется для диагностики (показывается, если плагин умер).

### Go SDK

Пакет `github.com/hotid/mpmtr/plugin` реализует протокол:

```go
plugin.Serve("http", "1", func(ctx context.Context, c net.Conn, req plugin.Request) plugin.Result {
	fmt.Fprintf(c, "HEAD / HTTP/1.0\r\nHost: %s\r\n\r\n", req.Host)
	line, err := bufio.NewReader(c).ReadString('\n')
	if err != nil {
		return plugin.Result{Stage: "answer", Err: err}
	}
	return plugin.Result{OK: strings.HasPrefix(line, "HTTP/")}
})
```

`cmd/mpmtr-app-http` — этот пример в виде полного плагина, с TLS на порту
443 и собственными опциями (`man mpmtr-app-http`). Проверка
проходит, когда сервер отвечает строкой состояния HTTP, с любым кодом: 503 —
тоже успех. Он показывает, что на сервере что-то говорит по HTTP, а не что
сервис работает; проверке вашего сервиса место в вашем собственном плагине.

## Плагины сведений о хопах

`mpmtr --hop-info ИМЯ` запускает исполняемый файл `mpmtr-hop-ИМЯ` (рядом с
mpmtr или в `PATH`; можно и `--hop-info ПУТЬ`); `--hop-info "ИМЯ АРГУМЕНТЫ..."`
передаёт плагину его собственные аргументы. Опцию можно указать несколько
раз: плагины работают одновременно.

mpmtr один раз передаёт каждому плагину адрес каждого показываемого хопа, а
плагин отвечает тем, что знает. С `--hop-info-interval D` (не меньше 1 с; по
умолчанию 0) адрес, который всё ещё на экране, спрашивается снова, когда
ответу исполнилось столько: старый ответ остаётся, пока не пришёл новый, а
новый пустой ответ его не стирает. Адрес, на который ответа не было,
переспрашивается с тем же интервалом. Ответы:

* `name` — показывается как имя хопа, `имя (адрес)`. Берётся имя от первого
  (в порядке командной строки) плагина, который его дал; имя от плагина идёт
  раньше имени из обратного DNS.
* `note` — короткий текст в колонке `PLUGIN` строки хопа (колонка есть
  только с `--hop-info`); тексты всех плагинов стоят рядом. Табуляция в
  подписи разделяет колонки: mpmtr дополняет их пробелами, чтобы одна и та
  же колонка начиналась в одном месте на всех строках
  (`Port-Channel37 err:0` над `Vlan754        err:0`).

И то и другое попадает в JSON-отчёт как `hop_info`: адрес → плагин → `name`,
`note`.

Сам mpmtr для этого никуда ничего не отправляет. Спрашивать ли про адрес,
где и с какими учётными данными — дело плагина и его собственной
конфигурации; у mpmtr для этого нет ни одной опции. Адреса хопов приходят из
сети: любой маршрутизатор на пути сам выбирает адрес, с которого отвечает,
поэтому плагину, который опрашивает само устройство, нужно явно указать,
какие адреса можно опрашивать. Плагин, который ошибся или умер, на измерение
не влияет: появляется предупреждение, и его подписи прекращаются.

### Протокол

Объекты JSON, по одному на строку: запросы — на stdin плагина, ответы — на
его stdout.

```
плагин → mpmtr  {"type":"hello","name":"snmp","version":"1"}
mpmtr → плагин  {"type":"hop","id":4,"addr":"192.0.2.1"}
плагин → mpmtr  {"type":"info","id":4,"name":"core1","note":"Eth1/2"}
```

* Сначала `hello`, в течение 5 с.
* Отвечать можно в любом порядке; на каждый запрос — ответ с его `id`, с
  пустыми `name` и `note`, если ничего не известно.
* Ответ позже 30 с игнорируется; итоговый отчёт ждёт ответов не дольше
  10 с.
* `name` обрезается до 64 символов, каждый столбец `note` — до 120; управляющие символы
  выбрасываются.
* Закончив, mpmtr закрывает stdin. stderr сохраняется для диагностики.

### mpmtr-hop-snmp

`mpmtr --hop-info "snmp ФАЙЛ"` спрашивает у маршрутизатора хопа его имя
(`sysName`) и интерфейс, которому принадлежит ответивший адрес (`ifName`): не
больше двух запросов GET на адрес, без обхода таблиц. С `--descr`
(`--hop-info "snmp --descr ФАЙЛ"`) после имени в «» идёт описание интерфейса
(`ifAlias`).

```
HOST                         …  PLUGIN
core1.example (192.0.2.1)    …  Ethernet1/2
core1.example (192.0.2.1)    …  Ethernet1/2 «to spine 3»     с --descr
```

ФАЙЛ задаёт, какие адреса можно опрашивать и как. На адрес, не попавший ни в
один префикс, не уходит ни одного пакета; из подходящих префиксов берётся
самый длинный. Файл не должен быть доступен на чтение группе и остальным
(`chmod 600`).

```
# SNMPv2c: community идёт открытым текстом на каждый опрашиваемый адрес
10.0.0.0/8      community=public
# SNMPv3
192.0.2.0/24    user=monitor auth=sha256:secret-one priv=aes:secret-two
# параметры, в любой строке: port=161 timeout=1s retries=1
```

`auth`: md5, sha, sha224, sha256, sha384, sha512; `priv`: des, aes, aes192,
aes256; пароли не короче 8 символов, без пробелов.

`--errors` (`--hop-info "snmp --errors ФАЙЛ"`, с `--descr` или без) добавляет
ошибки приёма на интерфейсе, в том же запросе:

* `crc:N` — кадры, не прошедшие контрольную сумму (`dot3StatsFCSErrors`);
* `err:N` — все входящие ошибки (`ifInErrors`), если у интерфейса нет
  счётчика контрольной суммы (port-channel, VLAN-интерфейс);
* ничего, если устройство не отдаёт ни того, ни другого.

Счётчики идут с загрузки устройства. Когда mpmtr спрашивает снова
(`--hop-info-interval`), добавляется прирост с первого запроса плагина:
`crc:1532 +12`. Если счётчик уменьшился (устройство перезагрузилось), отсчёт
начинается заново.

Интерфейс — тот, которому принадлежит ответивший адрес: обычно тот, через
который пришла проба, но маршрутизатор может отвечать и с другого интерфейса
или с loopback. Интерфейс, через который трафик уходит дальше, не
определяется.
